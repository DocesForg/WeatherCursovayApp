### 2.4.1. ER-диаграмма

ER-диаграмма (Entity-Relationship Diagram) представляет логическую структуру базы данных приложения. Диаграмма показывает сущности, их атрибуты и взаимосвязи между сущностями. База данных PostgreSQL содержит три основные таблицы: user_account для хранения учётных записей пользователей, favorite_city для избранных городов и support_message для сообщений поддержки.

Таблица user_account является центральной сущностью, к которой ссылаются остальные таблицы через внешние ключи. Каждая учётная запись имеет уникальный автоинкрементируемый идентификатор, уникальный адрес электронной почты, хэш пароля, отображаемое имя и роль. Ограничение UNIQUE на поле email гарантирует невозможность дублирования учётных записей с одинаковым адресом.

Таблица favorite_city хранит избранные города пользователей. Каждая запись связана с пользователем через внешний ключ account_id, ссылающийся на primary key таблицы user_account. Поля latitude и longitude хранят географические координаты для запросов к погодному API. Индексы на полях account_id и cityName оптимизируют выполнение запросов на выборку городов конкретного пользователя и поиск по названию.

Таблица support_message представляет сообщения в диалогах поддержки. Внешний ключ account_id связывает каждое сообщение с аккаунтом пользователя. Поле sender различает сообщения от пользователей и администраторов. Поле seen_by_admin отслеживает статус прочтения сообщения администратором. Индексы на account_id и created_at ускоряют выборку сообщений диалога в хронологическом порядке.

# База данных Bura


## DDL базы данных Bura

В проекте нет отдельных SQL-миграций Flyway/Liquibase или файла `schema.sql`: структура базы данных выводится из JPA-сущностей серверного модуля. Для разработки используется PostgreSQL и режим Hibernate `ddl-auto: update`, поэтому Hibernate может создавать и обновлять таблицы автоматически. Для production-профиля включен `ddl-auto: validate`, то есть приложение только проверяет соответствие уже существующей схемы описанию сущностей.

Ниже приведен DDL, эквивалентный текущим JPA-сущностям проекта для PostgreSQL.

```sql
CREATE TABLE user_account (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE,
    display_name VARCHAR(255) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    role VARCHAR(255) NOT NULL
);

CREATE TABLE favorite_city (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    account_id BIGINT NOT NULL,
    city_name VARCHAR(255) NOT NULL,
    latitude DOUBLE PRECISION NOT NULL,
    longitude DOUBLE PRECISION NOT NULL
);

CREATE TABLE support_message (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    account_id BIGINT NOT NULL,
    email VARCHAR(255) NOT NULL,
    name VARCHAR(255) NOT NULL,
    forward_to VARCHAR(255) NOT NULL,
    sender VARCHAR(255) NOT NULL,
    message VARCHAR(4000) NOT NULL,
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    seen_by_admin BOOLEAN NOT NULL
);

CREATE TABLE radio_signal_test (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    account_id BIGINT NOT NULL,
    city_a VARCHAR(255) NOT NULL,
    city_b VARCHAR(255) NOT NULL,
    distance_km DOUBLE PRECISION NOT NULL,
    path_loss_db DOUBLE PRECISION NOT NULL,
    quality VARCHAR(255) NOT NULL,
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL
);
```

### Связи и ограничения

Явные внешние ключи между таблицами в сущностях не описаны: поля `account_id` хранят идентификатор пользователя как обычное числовое поле. Поэтому на уровне DDL Hibernate создает только первичные ключи, `NOT NULL`-ограничения и уникальность `user_account.email`.

Индексы, кроме первичных ключей и уникального ограничения на email, в сущностях также не заданы. При необходимости ускорить выборки по `account_id`, `created_at` или `city_name` их можно добавить отдельными миграциями.

## ORM в проекте Bura

В серверной части Bura используется ORM-стек Spring Data JPA поверх Hibernate. Зависимость подключена через `spring-boot-starter-data-jpa`, а для подключения к СУБД используется PostgreSQL JDBC-драйвер.

### Используемые технологии

- **Jakarta Persistence API (JPA)** — стандарт аннотаций и API для описания сущностей (`@Entity`, `@Table`, `@Id`, `@Column`, `@GeneratedValue`).
- **Hibernate ORM** — реализация JPA, которая строит SQL-схему по сущностям и выполняет SQL-запросы.
- **Spring Data JPA** — слой репозиториев, который генерирует CRUD-операции и запросы по именам методов репозиториев.
- **PostgreSQL** — основная реляционная база данных проекта; в Docker Compose используется образ `postgres:16-alpine`.

### Конфигурация ORM

Активный профиль задается переменной `SPRING_PROFILES_ACTIVE`, по умолчанию используется `dev`.

В профиле разработки:

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: update
```

Hibernate сравнивает сущности с текущей схемой и пытается обновить структуру таблиц автоматически.

В production-профиле:

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

Hibernate не изменяет схему, а только проверяет, что таблицы и колонки соответствуют JPA-модели.

### Сущности JPA

#### `UserAccountEntity`

Сущность `UserAccountEntity` отображается на таблицу `user_account`. Она хранит email, отображаемое имя, хэш пароля и роль пользователя. Поле `email` помечено как уникальное, а все бизнес-поля обязательны.

#### `FavoriteCityEntity`

Сущность `FavoriteCityEntity` отображается на таблицу `favorite_city`. Она хранит избранный город пользователя: `accountId`, название города и координаты. Связь с пользователем хранится через числовое поле `accountId`, без JPA-аннотации `@ManyToOne`.

#### `SupportMessageEntity`

Сущность `SupportMessageEntity` отображается на таблицу `support_message`. Она описывает сообщение поддержки: пользователя, email, имя, адрес пересылки, отправителя, текст сообщения, дату создания и флаг просмотра администратором. Для поля `message` задана увеличенная длина `4000` символов.

#### `RadioSignalTestEntity`

Сущность `RadioSignalTestEntity` отображается на таблицу `radio_signal_test`. Она хранит историю расчетов радиосигнала: пользователя, два города, расстояние, потери сигнала, оценку качества и дату создания.

### Репозитории Spring Data JPA

Все репозитории наследуются от `JpaRepository<Сущность, Long>`. Благодаря этому проект получает стандартные операции `save`, `findById`, `findAll`, `deleteById` и другие без ручной реализации.

- `UserAccountRepository` работает с учетными записями и содержит методы поиска по email, проверки существования email и подсчета пользователей по роли.
- `FavoriteCityRepository` работает с избранными городами, выбирает записи пользователя, поддерживает поиск по части названия города без учета регистра и удаление всех записей пользователя.
- `SupportMessageRepository` работает с сообщениями поддержки, выбирает диалоги в хронологическом порядке, проверяет непрочитанные сообщения, считает сообщения и количество уникальных пользователей с обращениями. Для подсчета уникальных `accountId` используется JPQL-запрос через `@Query`.
- `RadioSignalTestRepository` работает с сохраненными расчетами радиосигнала и получает историю пользователя по дате создания в обратном порядке.

### Особенности модели данных

- В проекте используется подход простых сущностей: связи между таблицами представлены полями `Long accountId`, а не объектными связями JPA.
- Первичные ключи генерируются стратегией `GenerationType.IDENTITY`, что соответствует identity-колонкам PostgreSQL.
- Имена Java-полей в camelCase преобразуются Hibernate/Spring Boot в snake_case-колонки, например `displayName` становится `display_name`, а `createdAt` — `created_at`.
- Миграционный инструмент не подключен, поэтому для промышленной эксплуатации схему БД лучше фиксировать отдельными SQL-миграциями, особенно с учетом production-режима `ddl-auto: validate`.
