## 2. БИЗНЕС-КОНТЕКСТ

**Проблема:** Пользователям необходимо удобное мобильное приложение для отслеживания погодных условий и метеорологических данных с возможностью персонализации, сохранения избранных локаций и получения детализированной информации по различным параметрам (температура, влажность, давление, УФ-индекс, осадки и др.).

**Решение:** Система Bura предоставляет кроссплатформенное мобильное приложение на Android с современным интерфейсом (Jetpack Compose), которое синхронизируется с серверной частью на Spring Boot. Приложение поддерживает многопользовательский режим с JWT-аутентификацией, управление избранными городами, настройку тем оформления, отправку сообщений в поддержку и отображение расширенных метеоданных через модульную архитектуру.

## 3. ЦЕЛИ ПРОЕКТА

• Создать мобильное приложение для Android с интуитивным интерфейсом для отображения погодных данных

• Реализовать серверную часть с системой аутентификации, управлением пользователями и хранением данных

• Обеспечить модульную архитектуру приложения для поддержки различных метеорологических параметров (температура, влажность, давление, УФ-индекс, осадки, видимость, ветер и др.)

• Предоставить пользователям возможность персонализации (темы оформления, избранные локации, настройки единиц измерения)

• Реализовать систему обратной связи через службу поддержки

## Описание диаграмм IDEF0

**Контекстная диаграмма (A-0)** демонстрирует систему как единый чёрный ящик, показывая основные потоки данных:

- **Входы:** Пользовательские запросы на получение погодной информации, данные от внешних метеорологических сервисов, учётные данные для аутентификации.
- **Выходы:** Сформированные прогнозы погоды в различных форматах, статусы выполнения операций.
- **Управление:** Нормативные требования по защите персональных данных, спецификации REST API, бизнес-правила использования сервиса.
- **Механизмы:** Серверная инфраструктура на Spring Boot, мобильное приложение на Kotlin, внешние поставщики погодных данных.

**Декомпозиция (A0)** раскрывает четыре основных подпроцесса:

1. **Аутентификация и авторизация** - проверка учётных данных, выдача JWT-токенов, управление сессиями.
2. **Обработка запросов на погоду** - приём запросов от клиента, обращение к внешним API, агрегация и кэширование данных, формирование ответа.
3. **Управление избранными локациями** - добавление/удаление городов, синхронизация между устройствами, приоритизация отображения.
4. **Тест радиосвязи** - тестирование качества радиосвязи между двумя городами.


Диаграммы показывают, что система функционирует как посредник между пользователем и источниками погодных данных, обеспечивая безопасный доступ, персонализацию и своевременное информирование.

# Business Use Case диаграмма Bura

Файл `docs/00-project-charter/code-diagram/BUC.md` содержит бизнес-диаграмму вариантов использования Bura. В отличие от технической Use Case диаграммы, она описывает не внутренние экраны, API и хранилища приложения, а бизнес-цели участников и процессы, ради которых используется сервис.
<img src="/docs/00-project-charter/images/buc.png" alt="Business Use Case диаграмма">
## Участники бизнес-процессов

- **Клиент** — человек, который использует Bura для принятия бытовых или рабочих решений на основе погоды: выбрать одежду, спланировать прогулку, поездку, работу на улице или оценить условия в другом городе.
- **Оператор поддержки** — сотрудник, который отвечает на обращения клиентов и помогает решить проблемы, возникшие при использовании сервиса.
- **Администратор сервиса** — сотрудник с расширенными правами, который управляет клиентами, ролями и контролирует активность сервиса.
- **Погодный поставщик Open-Meteo** — внешний участник, предоставляющий погодные и географические данные, на которых строится пользовательская ценность Bura.

## Основные бизнес-процессы
Диаграмма показывает следующие бизнес-процессы:

1. **Получение актуальной погодной картины** — клиент выбирает интересующее место и получает понятную сводку текущих погодных условий.
2. **Планирование по прогнозу** — клиент оценивает погоду на ближайшие дни, чтобы заранее принять решение о поездках, прогулках или других активностях.
3. **Анализ динамики погоды** — клиент изучает изменения температуры, осадков и других показателей во времени.
4. **Работа с важными городами** — клиент сохраняет часто используемые города и быстро возвращается к ним.
5. **Персонализация представления данных** — клиент настраивает отображение погоды под свои привычки, например тему и единицы измерения.
6. **Управление клиентским аккаунтом** — клиент поддерживает актуальность данных аккаунта и контролирует доступ к сервису.
7. **Получение поддержки** — клиент отправляет обращение, а оператор поддержки обрабатывает его и помогает решить вопрос.
8. **Оценка радиосвязи между городами** — клиент оценивает возможность радиосигнала между двумя точками и может вернуться к прошлым оценкам.
9. **Администрирование сервиса** — администратор управляет клиентами, ролями и отслеживает активность по избранным городам, обращениям и радиотестам.

##№ Смысл связей на диаграмме

- `<<include>>` означает обязательный бизнес-шаг. Например, чтобы получить погодную картину, клиент должен выбрать интересующее место.
- `<<extend>>` означает дополнительный или условный сценарий. Например, быстрый возврат к сохраненному городу расширяет процесс работы с важными городами.

## Расчёт ROI

**Формула:** ROI = (Прибыль - Затраты) / Затраты × 100%

**Первый год:**
- Общие затраты: 486 000 + (4 300 × 12) = 537 600 руб
- Общий доход: 44 700 × 12 = 536 400 руб
- Прибыль: 536 400 - 537 600 = **-1 200 руб** (точка безубыточности)
- **ROI (год 1): -0.2%**

**Второй год (без учёта начальных затрат на разработку):**
- Затраты: 4 300 × 12 = 51 600 руб
- Доход (с ростом базы на 50%): 67 050 × 12 = 804 600 руб
- Прибыль: 804 600 - 51 600 = 753 000 руб
- **ROI (год 2): 1459%**

**Точка безубыточности:** 13-14 месяц после запуска
