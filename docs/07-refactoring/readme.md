# Рефакторинг проекта Bura

В этом разделе описано, какие **запахи кода** отслеживались в проекте Bura и как архитектурные паттерны **Data Mapper** и **Identity Map** помогают уменьшать связанность, дублирование и риск ошибок при работе с данными.

## 1. Запахи кода

Запах кода — это не обязательно ошибка, а признак того, что фрагмент программы может стать сложным для сопровождения, тестирования или расширения. В Bura мы рассматривали запахи кода как сигналы для рефакторинга: если код сложно прочитать, протестировать или изменить без побочных эффектов, его нужно упрощать.

### 1.1. Основные запахи, актуальные для проекта

| Запах кода | Как проявляется | Почему опасен | Что делали или планировали делать |
| --- | --- | --- | --- |
| **Long Method** | Метод выполняет много шагов подряд: получает данные, преобразует их, создает несколько объектов и возвращает итоговую модель | Сложно читать, тестировать отдельные части и безопасно менять логику | Разделять алгоритм на небольшие методы: подготовка данных, преобразование единиц, создание периодов, сборка результата |
| **Large Class / God Object** | Один класс отвечает сразу за несколько сценариев | Класс становится центром изменений и накапливает слишком много зависимостей | Выносить бизнес-логику в сервисы, репозитории и небольшие вспомогательные методы |
| **Duplicate Code** | Одинаковая логика преобразования DTO в Entity или Entity в Response повторяется в разных местах | При изменении формата данных нужно исправлять несколько участков кода | Использовать единые mapper-методы: `toDto`, `toEntity`, `toResponse` |
| **Primitive Obsession** | Значимые доменные понятия представлены простыми строками или числами | Легко передать некорректное значение, сложнее понять смысл параметра | Использовать enum, value object или отдельные DTO/Entity-классы |
| **Data Clumps** | Одни и те же группы параметров часто передаются вместе, например город + координаты | Сигнатуры методов становятся длинными, возрастает риск перепутать аргументы | Группировать связанные значения в request/response DTO или доменные классы |
| **Feature Envy** | Метод активно работает с данными другого объекта вместо поведения своего класса | Логика оказывается не там, где ее ожидает разработчик | Переносить поведение ближе к данным или выделять отдельный сервис/mapper |
| **Shotgun Surgery** | Для одной небольшой бизнес-правки нужно менять много файлов | Высокий риск пропустить часть изменений | Централизовать правила в сервисах, репозиториях и mapper-слое |

### 1.2. Примеры запахов в контексте Bura

#### Long Method в преобразовании прогноза

Клиентская логика прогноза содержит сложное преобразование входных погодных данных в набор доменных периодов: температура, ощущаемая температура, осадки, ветер, давление, видимость, влажность, условия погоды и солнце. Такой код естественно склонен к запаху **Long Method**, потому что один сценарий включает много однотипных операций.

Рефакторинг для такого участка:

1. вынести создание каждого периода в отдельный приватный метод;
2. оставить в основном методе только общий порядок сборки `Forecast`;
3. покрыть отдельные преобразования unit-тестами;
4. не смешивать конвертацию единиц, валидацию данных и сборку итогового объекта в одном блоке.

#### Primitive Obsession в ролях и статусах

На сервере роли пользователя могут храниться и передаваться как строковые значения. Такой подход прост, но при разрастании логики может привести к ошибкам из-за опечаток или невалидных значений. Поэтому для доменной логики предпочтительно использовать `AccountRole`, а строковое представление оставлять только на границе хранения или передачи данных.

#### Data Clumps в координатах и городах

В сценарии проверки радиосигнала часто передаются пары значений: `cityA`, `latitudeA`, `longitudeA` и `cityB`, `latitudeB`, `longitudeB`. Это типичный пример **Data Clumps**: параметры логически связаны, но передаются как отдельные поля. Улучшение — выделить объект, например `SignalEndpoint` или `GeoPointWithName`, чтобы метод принимал две точки, а не набор примитивных параметров.

#### Duplicate Code в преобразовании данных

В проекте есть несколько мест, где ответы backend API преобразуются в локальные Room Entity. Это нормальный слой интеграции, но если такие преобразования начинают повторяться, их лучше переносить в отдельные mapper-функции. Тогда изменение формата ответа или локальной таблицы будет требовать правки только в одном месте.

## 2. Подход к рефакторингу

Рефакторинг выполнялся не как переписывание проекта с нуля, а как постепенное улучшение кода без изменения внешнего поведения.

### 2.1. Общий алгоритм

1. **Найти запах кода** — длинный метод, дублирование, слишком большую ответственность класса или неудобную модель данных.
2. **Зафиксировать текущее поведение тестами** — сначала убедиться, что текущая логика описана unit-тестами или проверяется через API.
3. **Сделать маленькое изменение** — выделить метод, DTO, mapper или сервис.
4. **Запустить тесты** — проверить, что поведение не изменилось.
5. **Повторить** — улучшать код итерациями, не смешивая рефакторинг с новой функциональностью.

### 2.2. Правила, которых придерживались

- не менять публичный API без необходимости;
- не смешивать исправление дефекта и крупный рефакторинг в одном изменении;
- сохранять читаемость имен методов и DTO;
- выносить повторяющиеся преобразования в mapper-методы;
- оставлять бизнес-логику в сервисах и репозиториях, а не в UI-коде;
- после рефакторинга запускать тесты модуля, которого коснулось изменение.

## 3. Data Mapper

**Data Mapper** — это паттерн, который отделяет объектную модель приложения от структуры хранения данных. Его задача — преобразовывать объекты приложения в строки таблиц, JSON-ответы или другие форматы данных и обратно. Благодаря этому бизнес-логика не должна знать детали SQL, HTTP или конкретной схемы таблицы.

### 3.1. Зачем Data Mapper нужен в Bura

В проекте есть несколько представлений одних и тех же данных:

- backend entity — объект, который хранится в базе данных сервера;
- DTO/response — объект, который отправляется клиенту через REST API;
- remote DTO в Android-приложении — объект ответа Retrofit;
- локальная Room entity — объект, который сохраняется в SQLite на устройстве;
- доменная модель UI — объект, с которым работает экран или ViewModel.

Если смешать эти представления, код станет зависеть от деталей хранения и сетевого API. Data Mapper позволяет держать границы явными.

### 3.2. Data Mapper на сервере

На сервере роль Data Mapper частично выполняют Spring Data JPA и Hibernate:

- классы с `@Entity` описывают, как Java-объект связан с таблицей БД;
- `JpaRepository` скрывает SQL-операции за методами репозитория;
- сервис работает с объектами и репозиториями, а не с JDBC-запросами;
- DTO создаются отдельно и не отдаются наружу как JPA Entity.

Пример разделения:

```text
HTTP request -> Controller -> Service -> Repository -> JPA Entity -> Database
                                      -> DTO/Response -> HTTP response
```

Такой подход уменьшает связанность: изменение таблицы или способа получения данных не должно напрямую ломать контроллеры и клиентское API.

### 3.3. Entity -> DTO mapper

В серверной части используется явное преобразование Entity в DTO. Например, аккаунт хранит `passwordHash`, но ответ клиенту содержит только безопасные публичные поля: `id`, `email`, `displayName`, `role`. Это важная задача mapper-слоя: не раскрывать внутренние поля хранения наружу.

Преимущества такого подхода:

- API не зависит напрямую от структуры таблицы;
- можно скрыть чувствительные поля;
- легче менять формат ответа;
- проще тестировать сервисы и контроллеры.

### 3.4. Data Mapper в Android-модуле

В Android-приложении Data Mapper проявляется в двух местах:

1. **Room** преобразует строки SQLite в Kotlin-классы с `@Entity` и обратно.
2. **Repository-слой** преобразует remote DTO из backend API в локальные `AccountEntity`, `FavoriteCityEntity`, `SupportTicketEntity` и `RadioSignalTestEntity`.

Например, после входа или регистрации `AccountRepository` получает `AuthResponse` от backend API и сохраняет данные пользователя в локальную таблицу `account`. Для избранных городов, поддержки и истории радиосигнала используется похожий подход: ответ сервера преобразуется в локальную entity и сохраняется через DAO.

### 3.5. Когда стоит выделять отдельный mapper-класс

Пока преобразование короткое и используется в одном месте, его можно оставить рядом с репозиторием или сервисом. Отдельный mapper-класс стоит выделять, если:

- одно и то же преобразование повторяется в нескольких местах;
- mapping содержит условия, вычисляемые поля или форматирование дат;
- DTO и Entity часто меняются независимо;
- mapping сложно тестировать внутри большого сервиса.

Рекомендуемые имена:

```text
AccountMapper
FavoriteCityMapper
SupportMessageMapper
RadioSignalMapper
ForecastMapper
```

## 4. Identity Map

**Identity Map** — это паттерн, который гарантирует, что в рамках одного контекста работы с данными объект с одним и тем же идентификатором представлен одной и той же сущностью. Паттерн помогает избежать двух проблем:

1. повторной загрузки одного и того же объекта;
2. конфликтующих изменений в разных копиях одной записи.

### 4.1. Identity Map на сервере

На backend Identity Map используется инфраструктурно через JPA/Hibernate. В рамках persistence context Hibernate отслеживает загруженные entity по их primary key. Если одна и та же запись загружается повторно в рамках одного контекста, Hibernate может вернуть уже управляемый объект, а изменения такого объекта отслеживаются до сохранения/завершения транзакции.

Для проекта это полезно в сценариях:

- обновление имени пользователя;
- изменение пароля;
- удаление аккаунта и связанных данных;
- работа с entity, которые имеют `@Id` и управляются JPA.

Важно: в коде Bura нет отдельного самописного класса `IdentityMap`. Паттерн применяется через ORM-инструмент, поэтому разработчики используют репозитории и транзакции, а не вручную поддерживают `Map<ID, Entity>`.

### 4.2. Identity Map и локальный кэш Android

В Android-модуле Room-таблицы также используют первичные ключи. Например:

- аккаунт хранится по `id`;
- избранный город хранится по паре `accountId` + `id`;
- сообщение поддержки хранится по паре `accountId` + `id`;
- проверка радиосигнала хранится по паре `accountId` + `id`.

Это не полноценная in-memory Identity Map, но это выполняет похожую задачу на уровне локального кэша: одна запись имеет один стабильный ключ, а `upsert` с `OnConflictStrategy.REPLACE` обновляет существующую запись вместо создания дубликата.

### 4.3. Правила использования Identity Map-подхода

Чтобы не создавать конфликтующие копии данных, в проекте важно соблюдать правила:

1. все сущности, которые синхронизируются с сервером, должны иметь стабильный `id`;
2. для данных пользователя в локальной БД нужно учитывать `accountId`, чтобы не смешивать данные разных аккаунтов;
3. обновления должны проходить через repository/DAO, а не напрямую из UI;
4. после удаления аккаунта необходимо очищать локальные записи, связанные с этим аккаунтом;
5. если данные пришли с сервера повторно, нужно обновлять существующую запись, а не создавать новую.

## 5. Связь паттернов с качеством кода

Data Mapper и Identity Map помогают устранять или ослаблять запахи кода:

| Проблема | Как помогает Data Mapper | Как помогает Identity Map |
| --- | --- | --- |
| Дублирование преобразований | Централизует mapping между DTO, Entity и доменной моделью | Не решает mapping напрямую, но уменьшает дублирование объектов с одним id |
| Смешение бизнес-логики и хранения | Отделяет сервисы и UI от SQL/JSON-структур | Позволяет работать с одной управляемой entity в контексте данных |
| Ошибки при обновлении данных | Делает правила преобразования явными | Предотвращает конфликтующие копии одной записи |
| Сложность тестирования | Mapper можно тестировать отдельно | Упрощает проверку сценариев обновления и удаления |
| Shotgun Surgery | Изменения формата данных локализуются в mapper-слое | Стабильные ключи уменьшают количество мест, где нужно искать дубликаты |

## 6. Итог

В Bura рефакторинг направлен на то, чтобы код оставался понятным и безопасным для изменений. Запахи кода используются как индикаторы проблем, Data Mapper отделяет бизнес-логику от форматов хранения и передачи данных, а Identity Map-подход помогает работать с сущностями по стабильным идентификаторам и избегать дублирования записей.
