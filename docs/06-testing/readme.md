# Тестирование проекта Bura

В этом разделе описано, как в проекте Bura использовались три инструмента и подхода контроля качества: **тест-планы**, **JaCoCo** и **Postman**. Тестирование разделено на автоматические проверки мобильного приложения и серверной части, контроль покрытия кода, а также ручную/интеграционную проверку REST API.

## 1. Цели тестирования

Основные цели тестирования проекта:

- убедиться, что пользовательские сценарии приложения работают корректно: регистрация, вход, работа с аккаунтом, избранными городами, погодными данными, статистикой, поддержкой и проверкой радиосигнала;
- проверить бизнес-логику без запуска полного приложения там, где это возможно;
- защитить критичные серверные сценарии авторизации и управления данными от регрессий;
- получить измеримое представление о покрытии серверного кода тестами;
- вручную проверить реальные HTTP-запросы к API в условиях, близких к использованию клиентским приложением.

## 2. Тест-планы

Тест-планы использовались как основной документ для структурирования проверок. Для каждого функционального блока мы заранее определяли:

1. **Что проверяется** — модуль, экран, API-метод или бизнес-правило.
2. **Предусловия** — наличие пользователя, роль пользователя, токен авторизации, подготовленные данные в БД.
3. **Шаги проверки** — последовательность действий пользователя или HTTP-запросов.
4. **Ожидаемый результат** — корректный ответ, изменение состояния, ошибка в негативном сценарии.
5. **Тип проверки** — модульная, интеграционная, ручная через Postman.
6. **Статус** — пройдено, требует исправления, требует повторной проверки.

### 2.1. Общий тест-план проекта

| Раздел | Что проверяли | Тип проверки | Инструменты |
| --- | --- | --- | --- |
| Метеоданные и единицы измерения | Температура, влажность, давление, ветер, осадки, видимость, UV-индекс, конвертация единиц | Модульные тесты | JUnit, Kotlin tests |
| Формирование прогнозов | Преобразование данных прогноза в модели приложения, дневные/часовые сводки, графики | Модульные тесты | JUnit, coroutines test |
| Аккаунты | Регистрация, вход, роли USER/ADMIN, смена имени и пароля, удаление аккаунта | Модульные и API-тесты | JUnit, Mockito, Postman |
| Безопасность | JWT, фильтр авторизации, доступ пользователя только к своим данным, доступ администратора | Модульные тесты, ручная проверка API | JUnit, Spring Security Test, Postman |
| Избранные города | Добавление, список, поиск, редактирование и удаление городов | Интеграционные/контроллерные тесты и Postman | JUnit, Spring Test, Postman |
| Админ-панель | Получение статистики, список пользователей, изменение ролей | Контроллерные тесты и Postman | JUnit, Postman |
| Поддержка | Сообщения пользователя, просмотр диалогов администратором, ответы поддержки, очистка истории | Модульные/контроллерные тесты и Postman | JUnit, Postman |
| Радиосигнал | Расчет качества сигнала, история проверок, зависимость качества от path loss | Модульные тесты и Postman | JUnit, Postman |

### 2.2. Пример тест-плана для авторизации

| ID | Сценарий | Предусловие | Шаги | Ожидаемый результат |
| --- | --- | --- | --- | --- |
| AUTH-01 | Регистрация нового пользователя | Email отсутствует в БД | Отправить `POST /api/auth/register` с email, именем и паролем | Создан аккаунт с ролью `USER`, возвращен JWT |
| AUTH-02 | Регистрация администратора | Email совпадает с настроенным admin email | Отправить `POST /api/auth/register` для admin email | Создан аккаунт с ролью `ADMIN`, возвращен JWT |
| AUTH-03 | Вход с корректными данными | Пользователь существует | Отправить `POST /api/auth/login` | Возвращен JWT и данные аккаунта |
| AUTH-04 | Вход с неверным паролем | Пользователь существует | Отправить `POST /api/auth/login` с неправильным паролем | Возвращается ошибка авторизации |
| AUTH-05 | Доступ к чужому аккаунту | Есть два пользователя | Пользователь A запрашивает `GET /api/accounts/{id}` пользователя B | Запрос запрещен |

### 2.3. Пример тест-плана для избранных городов

| ID | Сценарий | Предусловие | Шаги | Ожидаемый результат |
| --- | --- | --- | --- | --- |
| FAV-01 | Добавление города | Пользователь авторизован | `POST /api/accounts/{accountId}/favorites` | Город сохранен, возвращен статус `201 Created` |
| FAV-02 | Получение списка | У пользователя есть избранные города | `GET /api/accounts/{accountId}/favorites` | Возвращается список городов пользователя |
| FAV-03 | Поиск по названию | В списке есть несколько городов | `GET /api/accounts/{accountId}/favorites/search?city=...` | Возвращаются только совпадающие города |
| FAV-04 | Редактирование города | Город принадлежит пользователю | `PUT /api/accounts/{accountId}/favorites/{favoriteId}` | Данные города обновлены |
| FAV-05 | Удаление города | Город принадлежит пользователю | `DELETE /api/accounts/{accountId}/favorites/{favoriteId}` | Город удален |
| FAV-06 | Попытка удалить чужой город | Город принадлежит другому пользователю | `DELETE /api/accounts/{accountId}/favorites/{favoriteId}` | Возвращается ошибка доступа или `404` |

### 2.4. Как тест-планы связаны с автотестами

Тест-планы не заменяли автоматические тесты, а задавали структуру проверок. После описания сценариев мы переносили стабильные и повторяемые проверки в код:

- в `app/src/test/java/com/docesforg/bura` находятся тесты клиентской логики: погодные сущности, периоды, сводки, графики, конвертер прогноза и расчет качества радиосигнала;
- в `server/src/test/java/com/docesforg/bura/server` находятся серверные тесты: аккаунты, избранные города, безопасность, JWT, админ-функции, статистика и поддержка;
- сценарии, где важно проверить полный HTTP-запрос, заголовки и тело ответа, дополнительно выполнялись вручную через Postman.

## 3. Автоматическое тестирование

### 3.1. Тесты мобильного приложения

В Android-модуле используются unit-тесты на Kotlin/JUnit. Они проверяют бизнес-логику без запуска UI:

- конвертацию температуры, давления, скорости ветра, осадков и видимости;
- расчет минимальных и максимальных значений по периодам;
- формирование сводок прогноза: текущей, дневной, почасовой, по солнцу, осадкам, давлению, видимости и другим показателям;
- подготовку данных для графиков;
- преобразование `ForecastData` в доменные модели приложения;
- расчет процента качества радиосигнала.

Запуск тестов приложения:

```bash
./gradlew :app:testDebugUnitTest
```

### 3.2. Тесты серверной части

Серверный модуль тестируется на Java/JUnit 5. Для изоляции зависимостей используются Mockito и Spring Security Test. Проверяются:

- хеширование пароля и выдача JWT при регистрации;
- отказ при неверном пароле;
- назначение роли администратора по настроенному email;
- порядок удаления связанных данных пользователя перед удалением аккаунта;
- правила доступа пользователя и администратора;
- генерация и проверка JWT;
- работа контроллеров избранных городов, статистики, поддержки и администрирования.

Запуск тестов сервера:

```bash
./gradlew :server:test
```

Полная проверка серверного модуля вместе с JaCoCo verification:

```bash
./gradlew :server:check
```

## 4. JaCoCo

JaCoCo используется в серверном модуле для измерения покрытия Java-кода автоматическими тестами.

### 4.1. Подключение JaCoCo

В `server/build.gradle.kts` подключен Gradle-плагин JaCoCo:

```kotlin
plugins {
    id("jacoco")
}
```

Также указана версия инструмента:

```kotlin
jacoco {
    toolVersion = "0.8.12"
}
```

### 4.2. Генерация отчетов

После выполнения задачи `test` автоматически запускается `jacocoTestReport`. Для отчетов включены два формата:

- **HTML** — удобен для просмотра покрытия по пакетам, классам и строкам кода;
- **XML** — пригоден для CI/CD, внешних анализаторов и публикации метрик.

Команда запуска:

```bash
./gradlew :server:test :server:jacocoTestReport
```

Основные файлы отчетов:

```text
server/build/reports/jacoco/test/html/index.html
server/build/reports/jacoco/test/jacocoTestReport.xml
```

### 4.3. Порог покрытия

В проекте задан минимальный порог покрытия серверного модуля — **40%**. Проверка выполняется задачей `jacocoTestCoverageVerification`, а задача `check` зависит от нее. Это значит, что при снижении покрытия ниже установленного порога сборка серверного модуля должна завершиться ошибкой.

Команда проверки покрытия:

```bash
./gradlew :server:jacocoTestCoverageVerification
```

### 4.4. Как использовался отчет JaCoCo

Отчет JaCoCo применялся для:

- поиска классов, которые еще не покрыты тестами;
- контроля критичных зон серверной логики: аккаунты, безопасность, поддержка, избранные города;
- проверки, что новые изменения не уменьшают покрытие ниже установленного порога;
- планирования следующих тестов: сначала покрывались классы с бизнес-логикой и ветвлениями, затем контроллеры и вспомогательные компоненты.

## 5. Postman

Postman использовался для ручного и интеграционного тестирования REST API серверной части. В отличие от unit-тестов, Postman позволяет проверить API так, как его вызывает клиентское приложение: с реальным URL, HTTP-методом, JSON-телом, заголовком `Authorization` и фактическим ответом сервера.

### 5.1. Подготовка окружения

Для локального запуска API использовался сервер на порту `8080`. Базовый адрес в Postman:

```text
http://localhost:8080
```

Рекомендуемые переменные окружения Postman:

| Переменная | Назначение | Пример |
| --- | --- | --- |
| `baseUrl` | Базовый URL сервера | `http://localhost:8080` |
| `token` | JWT пользователя или администратора | `eyJ...` |
| `accountId` | ID текущего аккаунта | `1` |
| `favoriteId` | ID избранного города | `10` |

Для защищенных запросов добавлялся заголовок:

```http
Authorization: Bearer {{token}}
```

### 5.2. Коллекция запросов Postman

Коллекция Postman была сгруппирована по функциональным разделам API:

#### Auth

- `POST {{baseUrl}}/api/auth/register` — регистрация пользователя;
- `POST {{baseUrl}}/api/auth/login` — вход и получение JWT.

Пример тела регистрации:

```json
{
  "email": "user@example.com",
  "displayName": "Test User",
  "password": "secret123"
}
```

После успешного ответа JWT сохранялся в переменную `token`, а идентификатор пользователя — в `accountId`.

#### Account

- `GET {{baseUrl}}/api/accounts/{{accountId}}` — получить данные аккаунта;
- `PATCH {{baseUrl}}/api/accounts/{{accountId}}/name` — изменить отображаемое имя;
- `PATCH {{baseUrl}}/api/accounts/{{accountId}}/password` — изменить пароль;
- `DELETE {{baseUrl}}/api/accounts/{{accountId}}` — удалить аккаунт.

#### Favorites

- `GET {{baseUrl}}/api/accounts/{{accountId}}/favorites` — список избранных городов;
- `GET {{baseUrl}}/api/accounts/{{accountId}}/favorites/search?city=Минск` — поиск по названию;
- `POST {{baseUrl}}/api/accounts/{{accountId}}/favorites` — добавить город;
- `PUT {{baseUrl}}/api/accounts/{{accountId}}/favorites/{{favoriteId}}` — обновить город;
- `DELETE {{baseUrl}}/api/accounts/{{accountId}}/favorites/{{favoriteId}}` — удалить город.

Пример тела для добавления города:

```json
{
  "cityName": "Minsk",
  "latitude": 53.9,
  "longitude": 27.5667
}
```

#### Stats

- `GET {{baseUrl}}/api/accounts/{{accountId}}/stats` — пользовательская статистика.

#### Radio tests

- `GET {{baseUrl}}/api/accounts/{{accountId}}/radio-tests` — история проверок радиосигнала;
- `POST {{baseUrl}}/api/accounts/{{accountId}}/radio-tests` — расчет качества радиосигнала между двумя точками.

Пример тела запроса:

```json
{
  "cityA": "Minsk",
  "cityB": "Warsaw",
  "latitudeA": 53.9,
  "longitudeA": 27.5667,
  "latitudeB": 52.2297,
  "longitudeB": 21.0122,
  "frequencyMhz": 900
}
```

#### Support

- `POST {{baseUrl}}/api/accounts/{{accountId}}/support/messages` — отправить сообщение в поддержку;
- `GET {{baseUrl}}/api/accounts/{{accountId}}/support/messages` — получить историю сообщений пользователя;
- `DELETE {{baseUrl}}/api/accounts/{{accountId}}/support/messages` — очистить историю пользователя.

Административные запросы поддержки:

- `GET {{baseUrl}}/api/admin/support/conversations` — список диалогов;
- `GET {{baseUrl}}/api/admin/support/accounts/{{accountId}}/messages` — история сообщений выбранного пользователя;
- `POST {{baseUrl}}/api/admin/support/accounts/{{accountId}}/messages` — ответ администратора.

#### Admin

- `GET {{baseUrl}}/api/admin/dashboard` — сводка для администратора;
- `GET {{baseUrl}}/api/admin/accounts` — список аккаунтов;
- `PATCH {{baseUrl}}/api/admin/accounts/{{accountId}}/role` — изменение роли пользователя.

### 5.3. Что проверялось через Postman

Через Postman выполнялись следующие виды проверок:

- **позитивные сценарии**: успешная регистрация, вход, создание избранного города, получение статистики, отправка сообщения в поддержку;
- **негативные сценарии**: неверный пароль, запрос без токена, запрос с токеном другого пользователя, попытка доступа к admin API без роли `ADMIN`;
- **проверка кодов ответа**: `200 OK`, `201 Created`, `204 No Content`, `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`;
- **проверка структуры JSON**: наличие `token`, `account`, `id`, `role`, списков избранного и сообщений;
- **проверка изменения состояния**: после `POST` объект появляется в списке, после `PUT` данные меняются, после `DELETE` объект отсутствует.

### 5.4. Пример Postman Tests-скриптов

Для запросов авторизации можно использовать скрипт, который автоматически сохраняет токен:

```javascript
pm.test("response is successful", function () {
    pm.response.to.have.status(200);
});

const json = pm.response.json();
pm.environment.set("token", json.token);
pm.environment.set("accountId", json.account.id);
```

Для защищенных запросов можно проверять, что ответ содержит данные текущего пользователя:

```javascript
pm.test("account id matches environment", function () {
    const json = pm.response.json();
    pm.expect(String(json.id)).to.eql(pm.environment.get("accountId"));
});
```

## 6. Итоговый процесс проверки

Перед завершением задачи использовался следующий порядок:

1. Обновить или добавить сценарии в тест-план.
2. Реализовать или обновить автотесты для повторяемых проверок.
3. Запустить тесты мобильного приложения при изменениях в клиентской логике.
4. Запустить тесты сервера и JaCoCo-проверку при изменениях в backend.
5. Проверить основные API-сценарии в Postman, если изменялись контроллеры, DTO, безопасность или формат ответов.
6. Зафиксировать результат: какие проверки пройдены, какие дефекты найдены и что требует повторной проверки.

Такой подход позволил совместить планирование тестирования, автоматическую защиту от регрессий и ручную проверку реального REST API.
